SecurePAM

A privileged-access gateway. Nobody connects to a server or an internal web app directly: a person asks, the system decides, grants a time-boxed window, and SecurePAM itself opens, records and cuts off the session. Click anything in the diagrams.

The system map

Two application pairs share one set of services. Pair A signs in with a dev password; pair B signs in through Keycloak with a one-time code. Select a box to see what it does and what it talks to.

How a request becomes a grant

One service, AccessDecisionService, runs the whole decision. The route only translates HTTP. Policy and risk are evaluated separately on purpose, so either can be tuned without touching the other.

Risk score, factor by factor

Deterministic rules, not machine learning: the same inputs always give the same score, and every factor carries its reason. Weights are this project's own and overridable by RISK_* settings.

How a session is launched and policed

SSH, RDP and the isolated browser share one launch pattern. The browser never touches the credential or the target: it only holds a one-time ticket for 60 seconds. Pick a protocol, then step through (arrow keys work).

Where credentials live and how they are used

A password is typed once into the GUI, kept only in OpenBao, and only ever handed to a protocol handshake on the server. The database stores a reference, never the secret.

The vault, as running

  • https://127.0.0.1:18210, TLS 1.2+, checked against a local CA.
  • Raft storage on disk, Shamir seal: 3 shares, any 2 unseal. It starts sealed after every restart.
  • File audit device; KV v2 mount secret/; credentials at secret/securepam/assets/kali and …/win11-lab.
  • Application tokens last 30 days, are non-renewable and orphaned.
